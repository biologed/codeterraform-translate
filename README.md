# Русификатор для Code: Terraform — Code: Terraform Translator
### Перевод Code:Terraform на русский язык, игры на движке Tauri через хук WebView2

DLL, которая внедряется в процесс игры (Tauri = Rust + системный WebView2)
и переводит её интерфейс. Переводов два, они работают независимо:

- **Через локаль самой игры** (основной, см. раздел «Перевод через локаль
  игры»). В игре есть система локализации: строки ищутся по ключу, а если
  перевода нет — показывается английский исходник из кода. DLL достаёт
  оригинальные js-чанки прямо из exe, врезает в функцию поиска перевода
  выдачу строк из `locale_ru.json` и отдаёт странице. Текст переводится ДО
  того, как попадёт на экран, поэтому написанное игроком (код в редакторе,
  вывод его программ) задеть невозможно в принципе, а строки с
  подстановками (`{count}`) работают сами собой. Ничего заранее готовить не
  нужно, обновления игры ничего не ломают.
- **Через подмену текста в DOM** (вспомогательный, словарь
  `translations.json`). Нужен для того, до чего локализация не дотягивается:
  строк, которые игра собирает в рантайме. Здесь текст игрока приходится
  защищать отдельно — см. «Почему не переводится то, что игрок написал сам».

## Как это работает (общая часть)

1. Хукаем функцию создания WebView2 environment. Она может лежать в двух
   местах: публичная `CreateCoreWebView2EnvironmentWithOptions` в
   `WebView2Loader.dll` (если игра использует динамический загрузчик), либо
   недокументированная (но подтверждённая справочником Microsoft webview2-idl)
   `CreateWebViewEnvironmentWithOptionsInternal` в `EmbeddedBrowserWebView.dll`
   самого рантайма (если загрузчик статически встроен в exe игры — как в
   этой игре). Перебираем все загруженные в процесс модули через Toolhelp32
   и хукаем то, что реально найдётся (через MinHook, `GetProcAddress`).
2. Когда игра её вызывает, подменяем колбэк создания environment на свой —
   получаем указатель на `ICoreWebView2Environment`.
3. У ЭТОГО конкретного объекта хукаем метод `CreateCoreWebView2Controller`
   напрямую в его таблице виртуальных функций (обычный `GetProcAddress`
   тут не подходит — это метод COM-объекта, а не экспорт DLL).
4. Когда игра создаёт контроллер, получаем `ICoreWebView2Controller` →
   `ICoreWebView2`.
5. Регистрируем через `AddScriptToExecuteOnDocumentCreated` скрипт, который
   сам запускается при каждой навигации ещё до скриптов страницы:
   он проходит по `document.body`, заменяет текст по словарю и ставит
   `MutationObserver`, чтобы ловить и то, что Tauri дорисует позже (SPA).
6. Обратный канал JS → DLL (для дампа текста) сделан через
   `window.chrome.webview.postMessage(...)` + `add_WebMessageReceived`.

Все эти шаги подробно закомментированы в коде (`dll/hooks.cpp`,
`dll/webview.cpp`, `dll/translate.cpp`) — читайте комментарии, там объяснено
"зачем", а не только "что".

## Установка (если вы просто хотите играть на русском)

Собирать ничего не нужно, достаточно трёх файлов рядом с `code-terraform.exe`:

| Файл | Откуда |
|---|---|
| `Translator.dll` | из релиза или собранный по инструкции ниже |
| `TranslatorLauncher.exe` | оттуда же |
| `locale_ru.json` | `locale/locale_ru.json` из этого репозитория |
| `Запустить с переводом.bat` | `install/` из этого репозитория |

Проще всего взять готовый архив из раздела Releases — там ровно эти файлы
одним плоским списком, распаковал в папку игры и всё.

Дальше запускайте игру через `Запустить с переводом.bat` вместо
`code-terraform.exe` (или настройте Steam Launch Options — см. «Внедрение в
игру», способ 3). Строки, которых ещё нет в `locale_ru.json`, игра покажет
по-английски — перевод можно пополнять постепенно.

Проверить, что всё сработало, можно в `translator_log.txt` рядом с DLL:
там должны быть строки `[gameassets] Ассетов игры найдено в exe: ...` и
`[assets] Подменён файл игры: ...`.

### Два файла перевода: рабочий и релизный

Переводить удобно в полном каталоге, где рядом с ключом виден английский
оригинал, — но игроку такой файл отдавать незачем: недостающие ключи игра
показывает по-английски сама. Поэтому файлов два, и оба лежат в репозитории:

| Файл | Что внутри | Зачем |
|---|---|---|
| `locale_ru.json` (корень) | полный каталог, ~1,7 МБ | в нём переводят; лежит в гите, чтобы продолжать работу с любой машины |
| `locale_en.json` (корень) | английский оригинал | нужен как эталон: по нему считается прогресс и проверяются ключи |
| `locale/locale_ru.json` | только переведённые строки, ~36 КБ | это и попадает в релиз и в папку игры |

Релизный файл получается из рабочего одной командой (она же в чек-листе
выпуска):

```
python tools/locale_sync.py export locale_ru.json locale_en.json locale\locale_ru.json
```

Обратная операция — собрать рабочий файл заново, если он потерялся или игра
обновилась и в каталоге появились новые ключи:

```
python tools/dump_strings.py "D:\...\code-terraform_assets" strings_out
python tools/locale_sync.py work strings_out\catalog.json locale\locale_ru.json locale_ru.json
```

Что в репозиторий не попадает вообще (см. `.gitignore`): сам
`code-terraform.exe`, распакованный из него фронтенд и промежуточные дампы.
Перевод от этого не зависит — он привязан к ключам, а не к файлам игры.

Учтите: рабочие файлы — это текст игры целиком, и правка одной строки даёт
диff на весь файл. Если репозиторий станет публичным и это будет мешать,
их можно убрать из гита (`git rm --cached locale_ru.json locale_en.json`),
вернув строки в `.gitignore`; на релизный файл и на сборку это никак не
влияет.

## Сборка

Нужны: Visual Studio 2022 (компонент "Разработка классических приложений
на C++"), [vcpkg](https://github.com/microsoft/vcpkg). Заголовок `WebView2.h`
приезжает через vcpkg-порт `webview2` — отдельно ставить NuGet-пакет
Microsoft.Web.WebView2 не нужно.

1. Установите vcpkg и зависимости (manifest-режим — `vcpkg.json` уже лежит
   в корне проекта, зависимости подтянутся сами на этапе `cmake -B build`):
   ```
   git clone https://github.com/microsoft/vcpkg
   .\vcpkg\bootstrap-vcpkg.bat
   ```
2. **Определите битность игры** (Диспетчер задач → вкладка "Подробности" →
   столбец "Разрядность", либо Process Hacker). Это критично: DLL и
   инжектор должны быть собраны под ту же архитектуру (x86 или x64), иначе
   `LoadLibrary` просто откажется грузить DLL.
3. Соберите (пример для x64):
   ```
   cd Translator
   cmake -B build -S . -A x64 -DCMAKE_TOOLCHAIN_FILE=<путь_к_vcpkg>/scripts/buildsystems/vcpkg.cmake
   cmake --build build --config Release
   ```
   Всё собранное складывается в одну папку `build/bin` — и DLL, и лаунчер, и
   то, что DLL читает при старте (`locale_ru.json`, `translations.json`).
   Никакой вложенности по целям и конфигурациям: содержимое `build/bin` можно
   целиком копировать в папку игры. Обратная сторона — Debug и Release пишут
   в один каталог и затирают друг друга; если нужны обе конфигурации сразу,
   делайте отдельные каталоги сборки (`cmake -B build-debug`).

   Собрать готовый к выкладке комплект:
   ```
   python tools/make_release.py
   ```
   Результат: `release/CodeTerraform-RU/` (плоский набор файлов + `SHA256SUMS.txt`)
   и такой же `release/CodeTerraform-RU.zip` для GitHub Releases. Ровно это же
   собирает CI, чтобы локальная и серверная сборки не расходились.
   Если удобнее работать в самой Visual Studio — откройте `Translator/` как
   папку (Open Folder), VS сама подхватит CMakeLists.txt. Заголовки WebView2
   при этом добавьте через "Project → Manage NuGet Packages" →
   `Microsoft.Web.WebView2`.
4. После сборки рядом с `Translator.dll` окажется скопированный
   `translations.json` (это делает `POST_BUILD`-шаг в CMake).

## Внедрение в игру

**ВАЖНО про тайминг.** WebView2 environment создаётся практически сразу при
старте игры — ещё до того, как успевает показаться окно. Если внедрить DLL
в УЖЕ запущенную игру (когда меню уже видно), момент создания environment
уже прошёл, хук установится, но ловить будет нечего до следующего перезапуска
игры. Поэтому DLL нужно внедрять ДО старта игры, а не после.

Почему нельзя просто подложить фальшивую системную DLL (`version.dll`,
`dwmapi.dll` и т.п.) рядом с exe, как в классических DLL-инжект-модах: эта
игра грузит нужные системные библиотеки через `LoadLibraryExW` с флагом
`LOAD_LIBRARY_SEARCH_SYSTEM32` (видно в дизассемблере) — этот флаг явно
запрещает поиск DLL в папке приложения, только System32. Такой трюк тут
работать не будет. Поэтому нужен инжектор (или обёртка вокруг него) —
дальше три способа его использовать, от "запускать руками" до "вообще не
задумываться".

### Способ 1 — вручную каждый раз (для тестов/отладки)

```
TranslatorLauncher.exe --launch "D:\путь\к\code-terraform.exe" "D:\путь\к\Translator.dll"
```
Игру саму по себе запускать не нужно — инжектор запустит её сам.

### Способ 2 — ярлык/bat-файл (для повседневной игры без Steam)

Рядом с игрой уже лежит `Запустить с переводом.bat` — просто дважды
кликайте его вместо `code-terraform.exe`. Внутри — та же команда из
способа 1, но с путями, которые вычисляются автоматически (`%~dp0` —
папка самого .bat), так что при переносе игры в другое место ничего
руками поправлять не нужно. При желании сделайте на этот .bat обычный
ярлык Windows (правой кнопкой → "Отправить" → "Рабочий стол (ярлык)") и
дайте ему любую иконку.

### Способ 3 — Steam Launch Options (рекомендуется, если игра из Steam)

Настраивается один раз, дальше обычная кнопка "Играть" в Steam сама всё
делает — файлы игры при этом не трогаются и переживают обновления.

1. ПКМ по игре в библиотеке Steam → **Свойства** → **Общие** → **Параметры
   запуска**.
2. Вставьте (свои пути, с кавычками, `%command%` — оставить как есть, Steam
   сам его заменит на настоящую команду запуска игры):
   ```
   "D:\путь\к\TranslatorLauncher.exe" --launch-cmdline "D:\путь\к\Translator.dll" %command%
   ```
3. Закройте окно свойств и жмите "Играть" как обычно.

Режим `--launch-cmdline` (в отличие от `--launch`) принимает не ровно два
аргумента, а произвольную командную строку целиком — именно так, как Steam
подставляет `%command%` (там может быть не только путь к exe, но и
собственные параметры запуска игры).

После инжекта (любым способом) проверьте `translator_log.txt` рядом с DLL —
там пошагово видно, что произошло (найден ли модуль с нужным экспортом,
сработали ли хуки, сколько строк перевода загружено и т.д.).

## Использование

- **F6** — перечитывает `locale_ru.json` и перезагружает страницу, чтобы
  новый перевод собрался и применился без перезапуска игры. Страница при
  этом возвращается в исходное состояние — это инструмент переводчика, а не
  способ играть.
- **F7** — записывает в `dump_focus.txt` (и коротко в лог), что за элемент
  сейчас под курсором мыши и под фокусом: путь в DOM, классы, защищён ли он
  от перевода и каким именно селектором. Так подбираются `skipSelectors`
  (см. ниже): наведите мышь на панель, где перевод трогать нельзя, нажмите
  F7 и возьмите из файла готовую подсказку.
- **F9** — сохраняет `document.body.innerText` текущей страницы в `dump.txt`
  и НАКАПЛИВАЕТ в `dump_dom.json` заготовку словаря по текущему экрану:
  туда попадают только строки, которые реально переводятся (зоны
  пользовательского ввода пропускаются) и которых ещё нет в
  `translations.json`. Значения там = оригиналам, правьте их на русский и
  переносите к себе. Но основной способ собрать строки — офлайновый,
  см. «Как вытащить строки из игры».
- **F10** — сохраняет РАЗМЕТКУ (`document.body.outerHTML`, не только текст)
  в `dump_html.txt`. Нужен, когда конкретная фраза не переводится: F9 покажет
  только текст, а F10 — из каких именно тегов (`<span>`/`<p>`/`<div>`) она
  реально состоит. Работает через обычный `ExecuteScript` (не через DevTools,
  которые в этой игре чем-то заблокированы, а искать причину в реестре не
  дало результата) — так что это основной способ смотреть DOM-структуру.
- Правите `translations.json` (формат ниже, ключ — ТОЧНО как строка выглядит
  в интерфейсе после `.trim()`).
- **F11** — перечитывает `translations.json` и сразу применяет перевод,
  без перезапуска игры.

## Формат translations.json

Поддерживаются два варианта. Плоский, как раньше:

```json
{"Start Game": "Начать игру"}
```

и с настройками (в файле разрешены комментарии `//`):

```json
{
  "settings": {
    "skipSelectors": [".cm-editor", ".console-line-output"]
  },
  "translations": {
    "Continue": "Продолжить",
    "boot": {"to": "загрузка", "only": ".docs-panel-root"}
  }
}
```

- `settings.skipSelectors` — зоны, которые нельзя переводить (см. следующий
  раздел). Список ДОПОЛНЯЕТ встроенный; чтобы встроенный не применялся,
  добавьте `"useDefaultSkipSelectors": false`.
- Значение в словаре может быть объектом:
  `"to"` — перевод, `"only"` — переводить только внутри этого CSS-селектора,
  `"except"` — не переводить внутри него.

## Почему не переводится то, что игрок написал сам

Перевод работает по DOM: любой текстовый узел, совпавший со строкой словаря,
заменяется. Но игрок в этой игре сам пишет текст — код в редакторе и команды,
чей вывод попадает в консоль. Раньше словарь «переводил» и его: набранное в
редакторе `ON` превращалось в `ВКЛ` (и код переставал работать), а слово
`boot` нельзя было перевести в разделе помощи, не сломав ввод команды.

Теперь перед заменой проверяется, не находится ли узел в зоне
пользовательского ввода. Защита тройная:

1. **Встроенный список** (`kDefaultSkipSelectors` в `translate.cpp`): поля
   ввода, `contenteditable`, `role="textbox"`, популярные веб-редакторы кода
   и терминалы, плюс стандартные пометки `translate="no"`/`data-no-translate`.
2. **Ваш список** — `settings.skipSelectors`. Для этой игры туда уже вписаны
   `.cm-editor` / `.cm-content` (редактор кода — это CodeMirror),
   `.console-line-output` (вывод программы игрока; сообщения самой игры в
   консоли — `.console-line-system/-error/-warn` — переводятся) и
   `.player-copy-surface`. Новые подбираются хоткеем F7 и НЕ требуют
   пересборки DLL — достаточно F11.
3. **Элемент под фокусом** — если игрок прямо сейчас печатает в каком-то
   редактируемом элементе, его содержимое не трогается, даже если селектор
   этого редактора нигде не описан.

Атрибуты (`placeholder`, `title`, `aria-label`, `alt`) — это подписи от игры,
а не текст игрока, поэтому список зон ввода их не блокирует: они не
переводятся только там, где стоит явная пометка
`translate="no"`/`data-no-translate` (и внутри поддеревьев, которые игра
дорисовывает уже ВНУТРИ такой зоны — туда перевод не заходит вообще, чтобы
не бегать по DOM на каждое нажатие клавиши в редакторе). А вот атрибут
`value` трогается только у кнопок (`input[type=button|submit|reset]`), потому
что у обычного поля ввода `value` — это ровно то, что набрал игрок.

Слово, которое одновременно является командой игры, переводится через
ограничение по разделу — `{"to": "...", "only": "..."}`, см. пример с `boot`
выше.

Проверить всё это можно без запуска игры:

```
cd Translator/tools/jstest
npm install
npm test
```

Тест берёт настоящий скрипт из `translate.cpp` и настоящий
`translations.json`, разворачивает игрушечный DOM (редактор, консоль,
раздел помощи) и проверяет, что интерфейс переводится, а текст игрока — нет.

## Как вытащить строки из игры

Ходить по экранам с F9 больше не обязательно. В игре есть полноценная
система локализации: строки лежат в одном каталоге вида
`{"группа": {"ключ": "текст"}}`, а код зовёт их по ключу. Каталог вшит в
`code-terraform.exe` — вместе со всем фронтендом, сжатым brotli (поэтому
обычный поиск строк по exe ничего и не находит).

```
pip install brotli
python tools/extract_assets.py "D:\путь\к\code-terraform.exe"
python tools/dump_strings.py "D:\путь\к\code-terraform_assets" strings_out
```

- `extract_assets.py` находит в секции `.rdata` таблицу ассетов Tauri
  (записи по 32 байта: указатель на имя, длина, указатель на данные, длина),
  распаковывает brotli и раскладывает файлы по папкам — получается обычный
  фронтенд: `index.html`, `assets/*.js`, `*.css`, шрифты. Идея разбора
  таблицы — из [гиста liquidhelium](https://gist.github.com/liquidhelium/0b03392e4e2ddd8c9600b2c89e55e300),
  здесь переписано на Python и под 64-битные указатели.
- `dump_strings.py` находит в js-чанках каталог локализации (по форме:
  объект групп, внутри только строки — ровно так его проверяет и сама игра),
  разворачивает ссылки и спреды и кладёт рядом:
  - `catalog.json` / `catalog.flat.json` — все строки с ключами;
  - `translations.skeleton.json` — заготовка словаря
    `{"English text": "English text"}`, правьте правую часть;
  - `strings_with_placeholders.txt` — строки с подстановками (`{name}`),
    точным словарём они не ловятся, вынесены отдельно.
- `python tools/dump_strings.py <папка_ассетов> --merge <ваш translations.json>`
  дописывает только НОВЫЕ строки, не трогая уже переведённые — удобно после
  обновления игры.

На текущей версии игры так достаётся 12 484 строки (из них 9 380 без
подстановок). Пара групп собирается игрой только в рантайме — их по-прежнему
ловит F9.

## Перевод через локаль игры — основной способ

В игре есть штатная система локализации: строки лежат каталогом
`{группа: {ключ: текст}}`, код зовёт их по ключу, есть выбор языка на старте
и фолбэк на английский для ненайденных ключей. Просто языков в реестре
пока один. Если добавить туда русский каталог, переводит **сама игра**, ещё
до того как текст попадёт на страницу. Что это даёт по сравнению со
словарём по DOM:

- текст игрока (код в редакторе, вывод его программ) не может быть задет
  в принципе — DOM никто не трогает;
- работают строки с подстановками (`"Осталось {count} с"`) — они собираются
  уже из русского шаблона;
- ключи без перевода сами показываются по-английски — это штатный фолбэк
  игры, ничего доделывать не нужно, словарь можно наполнять постепенно.

Как это устроено. В js-чанках игры по ФОРМЕ (имена после минификации
меняются от сборки к сборке, форма — нет) находятся две функции:

- **функция поиска перевода** `w(ключ, язык)` — главная точка внедрения.
  Через неё проходят все пути перевода: и обычный `t(ключ)`, и вариант с
  английским исходником прямо в коде, и множественные числа. В начало её
  тела вставляется выдача нашей строки;
- **функция инициализации локалей** — вспомогательная: игра её вообще не
  вызывает (см. ниже), но если когда-нибудь вызовет — наш язык станет
  активным по-честному, вместе с Intl-форматами и правилами множественного
  числа.

Важно, почему главная точка именно поиск, а не инициализация: **игра
локаль не инициализирует вообще**. Английский текст лежит прямо в коде
рядом с ключами и подставляется как запасной вариант, если перевод не
нашёлся. То есть система работает «наоборот»: не «загрузили язык и
показали», а «спросили перевод, не нашли — показали исходник». Патч
инициализации при этом честно применялся, но никогда не исполнялся.

Файлы игры не меняются. Всё происходит в памяти, при запросе файла
страницей:

1. `dll/gameassets.cpp` достаёт ОРИГИНАЛ чанка из самой игры. exe уже
   загружен в наш процесс, поэтому его секцию `.rdata` можно читать прямо по
   указателям, без обращений к диску: там лежит таблица ассетов Tauri
   (записи по 32 байта — указатель на имя, длина, указатель на данные,
   длина), а в ней — сжатые brotli файлы фронтенда. Опорная точка — строка
   `/index.html`, от неё таблица разматывается в обе стороны.
2. `dll/locale.cpp` находит в распакованном чанке функцию поиска перевода
   (по форме, разбирая минифицированный код токен за токеном) и врезает в
   неё выдачу нашей строки, а рядом — сам каталог из `locale_ru.json`.
3. `dll/assets.cpp` отдаёт получившийся файл странице через
   `AddWebResourceRequestedFilter` + `add_WebResourceRequested`.

**Поэтому обновления игры больше ничего не ломают**: имена чанков с хешами
нигде не зашиты, оригиналы берутся из текущего exe, а патч ставится по форме
кода. Заранее ничего готовить не нужно — только `locale_ru.json` рядом с DLL.

Распаковка чанка (до нескольких мегабайт) идёт в фоновом потоке, результат
кэшируется в памяти; чанки, в которых нужной функции нет, запоминаются как
неподходящие и больше не трогаются.

**Отдельная тонкость про подмену.** Свой обработчик того же события есть и
у самой игры: Tauri (wry) обслуживает через него протокол
`http://tauri.localhost` и отдаёт файлы, вшитые в exe. До страницы доходит
ответ того, кто выставил его ПОСЛЕДНИМ, и простая запись ответа этот спор
проигрывала: в лог писалось «файл подменён», а страница получала оригинал
(было видно по размеру — 4 677 байт вместо наших мегабайт). Порядок
регистрации обработчиков не помогает, игра ставит свой позже в любом
случае. Решение — `GetDeferral()`: ответ выставляется отложенно, из очереди
сообщений окна игры, то есть уже после всех её обработчиков.

### Порядок действий

Один раз — получить файл, который вы будете переводить:

```
python tools/extract_assets.py "D:\...\code-terraform.exe"
python tools/dump_strings.py "D:\...\code-terraform_assets" strings_out
copy strings_out\catalog.json locale_ru.json
```

`locale_ru.json` — это тот же каталог с английскими значениями; правьте
значения на русские. Пустые значения пропускаются: такие ключи останутся
английскими. Файл привязан к КЛЮЧАМ, а не к файлам игры, поэтому переживает
любые обновления и переносится между версиями как есть.

Дальше просто **положите `locale_ru.json` рядом с `Translator.dll`** — всё,
больше ничего собирать не нужно, DLL сделает остальное при запуске игры.
Правки применяются по **F6** (перечитать каталог и перезагрузить страницу)
или при следующем запуске игры. В `translator_log.txt` появится:

```
[locale] locale_ru.json загружен, строк перевода: 12484
[assets] Подмена файлов игры включена: строк перевода 12484, готовых файлов в locale_patch 0
[gameassets] Ассетов игры найдено в exe: 853
[assets] Подменён файл игры: assets/i18n-Dh-M7E2V.js (1734348 байт, собран из exe на лету)
```

Проверять руками ничего не нужно: через пять секунд после загрузки страницы
DLL сама спрашивает у игры, чем всё закончилось, и пишет в лог строку вида

```
[webview] ExecuteScript результат: {"documentLang":"ru","patchLoaded":1,
  "localeApplied":{"keys":12484},"localeError":null,
  "loadedJs":["i18n-Dh-M7E2V.js:3383000"],"screen":"Continue\nНовая игра..."}
```

Как её читать (порядок важен, каждое поле отсекает свою причину):

| Поле | Что значит |
|---|---|
| `patchLoaded: null` | страница выполнила НЕ наш файл. Сверьте `loadedJs`: размер оригинала — килобайты, нашего патча — мегабайты |
| `localeApplied: null` при `patchLoaded: 1` | наш файл исполнился, но врезка не сработала — смотрите `localeError` |
| `localeError` | текст исключения из врезки |
| `screen` | первые символы экрана — сразу видно, перевелось или нет |

### Обновления игры (ранний доступ)

Ничего делать не нужно: оригиналы чанков берутся из текущего exe, а патч
ставится по форме кода, а не по именам файлов. Обновилась игра — перевод
просто продолжает работать.

Сломаться это может только если авторы поменяют саму систему локализации
(перепишут функцию поиска перевода) или формат вшитых ассетов. Тогда игра
работает как обычно, просто по-английски, а в логе будет видно, на каком
шаге всё встало:

```
[gameassets] Опорная строка "/index.html" в .rdata не найдена   <- изменился формат ассетов
[assets] ВНИМАНИЕ: страница загрузилась, но ни один файл подменить не удалось
```

Во втором случае форму функции нужно поправить в `dll/locale.cpp`
(`MatchLookupFunction`) — и там же лежит подробный комментарий, что именно
она ищет. Тот же поиск, но на Python, есть в `tools/make_locale_patch.py`
(`LOOKUP_RE`) — на нём удобнее экспериментировать, не пересобирая DLL.

### Заготовленные файлы вместо автопатча (запасной режим)

Если нужно подложить в игру произвольный собственный js (например,
поэкспериментировать с патчем руками), положите файл в папку `locale_patch`
рядом с DLL, повторив путь как в игре: `locale_patch/assets/имя.js`. Такие
файлы имеют приоритет над автопатчем.

Собрать их можно старым способом:

```
python tools/update_patch.py "D:\...\code-terraform.exe" locale_ru.json "D:\...\CodeTerraform"
```

Ключ `--pseudo` оборачивает каждую строку в «ёлочки» — быстрый способ
увидеть, какие надписи вообще проходят через локализацию. Помните, что
после обновления игры такие файлы придётся пересобирать (у автопатча этой
проблемы нет).
Если после запуска интерфейс в «ёлочках» — подмена работает, и дальше это
уже вопрос наполнения `locale_ru.json`. Полезные ключи: `--tag` (код языка,
по умолчанию `ru`), `--check catalog.json` (сверить ключи с английским
каталогом и показать опечатки).

Словарь по DOM (`translations.json`) при этом никуда не девается и работает
параллельно — он нужен для того, что мимо локалей: строки, которые игра
собирает в рантайме, и вообще любой текст, до которого система локализации
не дотягивается.

## Выпуск новой версии перевода

Перевод и код живут независимо: DLL пересобирать из-за новых строк не нужно,
она читает `locale_ru.json` при запуске игры. Всё, что требуется, - выгрузить
перевод из рабочего файла и поставить тег.

**1. Посмотреть, сколько сделано** (не обязательно, но приятно):

```
python tools/merge_translation.py locale_ru.json --progress --check locale_en.json
```

**2. Выгрузить перевод в репозиторий.** Рабочий файл `locale_ru.json` - полный
каталог, в гит идёт только переведённое:

```
python tools/locale_sync.py export locale_ru.json locale_en.json locale\locale_ru.json
```

**3. Проверить в игре.** Скопировать `locale\locale_ru.json` в папку игры и
нажать F6 (перечитать каталог и перезагрузить страницу) - или просто запустить
игру заново. В `translator_log.txt` должно быть `[locale] locale_ru.json
загружен, строк перевода: N` с новым числом.

**4. Закоммитить и запушить:**

```
git add locale/locale_ru.json
git commit -m "Перевод: ..."
git push
```

**5. Поставить тег - и всё остальное сделает CI:**

```
git tag v0.2.0
git push origin v0.2.0
```

По тегу сборка соберёт DLL с лаунчером, сложит комплект, подпишет
происхождение, создаст релиз (если его ещё нет) и приложит
`CodeTerraform-RU.zip` с `SHA256SUMS.txt`.

Чего делать НЕ нужно: `update_patch.py` и `make_locale_patch.py` для этого не
запускаются - DLL собирает патч сама, прямо из exe игры. Они остались только
как запасной режим (см. «Заготовленные файлы вместо автопатча»).

Перед тегом стоит поднять версию в `CMakeLists.txt` (`project(Translator
VERSION ...)`) - она попадает в свойства файлов, и пользователю по ней видно,
что у него за сборка.

## Антивирус ругается — что с этим делать

Жалобы на «троян» в `Translator.dll` и лаунчере — это ложные срабатывания, и
важно понимать, что полностью убрать их нельзя. Причина не в том, что мод
делает что-то плохое, а в том, КАК он это делает:

- чтобы перевести интерфейс изнутри игры, DLL нужно загрузить в чужой
  процесс. Связка `CreateProcess(CREATE_SUSPENDED)` + `VirtualAllocEx` +
  `WriteProcessMemory` + `CreateRemoteThread(LoadLibraryW)` — учебный пример
  внедрения DLL, и именно по нему эвристики опознают вредоносные программы.
  Отличить «внедрение ради перевода» от «внедрения ради кражи паролей»
  автоматически невозможно;
- внутри DLL стоят инлайн-хуки (MinHook правит код в памяти) — тот же
  разговор;
- файлы не подписаны сертификатом, и у них нет репутации: SmartScreen
  показывает «Неизвестный издатель» просто потому, что этот файл мало кто
  скачивал.

Единственное радикальное решение — **подпись сертификатом** (OV — примерно
$200–400 в год, EV — дороже, но даёт репутацию в SmartScreen сразу). Для
бесплатного мода это обычно неоправданно, поэтому дальше — то, что реально
делается без денег и что уже сделано в проекте.

### Что уже сделано

| Мера | Зачем |
|---|---|
| У DLL и лаунчера есть описание, версия, автор и ссылка на исходники (`cmake/version.rc.in`) | Безымянный бинарник без метаданных — сам по себе повод для эвристики и для недоверия. Теперь в «Свойствах» файла видно, что это и откуда |
| `injector.exe` переименован в `TranslatorLauncher.exe` | Слово «injector» читается как подтверждение худших опасений, хотя файл просто запускает игру |
| Сборка на GitHub Actions с `attest-build-provenance` | Любой может проверить, что выложенный бинарник собран из этого исходного кода: `gh attestation verify Translator.dll -R <владелец>/<репозиторий>` |
| `tools/make_release.py` кладёт рядом `SHA256SUMS.txt` | Пользователь сверяет хеш и знает, что скачал именно то, что выложил автор |
| `install/README.txt` в архиве | Объясняет игроку причину тревоги ДО того, как он испугается, и перечисляет, чего мод не делает |

### Чек-лист перед выпуском релиза

1. Подставьте свой репозиторий в `TRANSLATOR_URL` (корневой `CMakeLists.txt`)
   и имя автора в `TRANSLATOR_AUTHOR` — они попадут в свойства файлов.
2. Соберите релиз через CI, а не локально: так к файлам прикладывается
   подпись происхождения.
3. Выпуск делается **тегом**, а не веткой: релиз в GitHub привязан именно к
   тегу, и шаг CI «Приложить архив к релизу» срабатывает только на нём.
   ```
   git tag v0.2.0
   git push origin v0.2.0
   ```
   CI соберёт комплект, при необходимости создаст сам релиз и приложит к нему
   `CodeTerraform-RU.zip` и `SHA256SUMS.txt`. При обычном пуше в `main` этот
   шаг пропускается — там собранный комплект доступен артефактом на странице
   запуска (хранится 90 дней, виден только тем, кто зашёл в Actions).
   Локально то же самое собирает `python tools/make_release.py`.
4. Выложите **только через GitHub Releases**. Файлообменники и зеркала
   ломают всю цепочку доверия: проверить там нечего.
5. В описании релиза сразу напишите: что мод делает, что он внедряет DLL,
   почему антивирус может ругаться, хеши файлов и команду проверки
   происхождения. Вопрос «это точно не вирус?» лучше закрыть до того, как
   его зададут.
6. Отправьте свежие файлы как ложное срабатывание — это чинит проблему для
   всех, кто скачает после вас:
   - Microsoft Defender: <https://www.microsoft.com/en-us/wdsi/filesubmission>
   - остальные антивирусы принимают заявки на своих сайтах;
   - полезно предварительно прогнать файл через VirusTotal и приложить
     ссылку: сразу видно, какие движки и на что реагируют.

### Что отвечать пользователям

Коротко и по делу: это ложное срабатывание на технику внедрения DLL, без
которой перевод не попадёт внутрь игры; исходный код открыт, сборку делает
CI, хеши опубликованы, файл можно собрать самому. Если антивирус всё равно
удаляет файлы — добавить папку игры в исключения.

Чего делать НЕ стоит: паковать бинарник упаковщиками вроде UPX (это
однозначно ухудшит ситуацию) и просить людей «просто отключить антивирус».

## Известные ограничения / что доделать дальше

- Перевод ищет **точное** совпадение строки (после обрезки пробелов).
  Строки с динамическими вставками (`"Урон: 42"`, `"Уровень {n}"`) им не
  ловятся — для них нужны отдельные правила (например, регулярки в
  `translate.cpp` вместо точного словаря).
- Индекс `3` для `CreateCoreWebView2Controller` в таблице виртуальных
  функций взят из текущего порядка методов в `WebView2.h`. Если после
  обновления WebView2 SDK хуки перестанут срабатывать — это первое, что
  стоит перепроверить.
- Подмена локали (см. раздел про `locale_patch`) добавляет язык в саму
  игру, но НЕ показывает его в списке языков в настройках: реестр локалей
  лежит в другом (большом) чанке, и мы его не трогаем. Игра считает, что
  язык по-прежнему один; на переводе это не сказывается, но если захочется
  переключаться из настроек — патчить нужно будет и реестр `rs`
  (`{en: {definition: {...}, load: async () => каталог}}`) в
  `textContextMenu-*.js`.
- Запуск игры напрямую (не из Steam) заканчивается тем, что она
  перезапускает себя через Steam, и внедрённая DLL остаётся в умершем
  процессе — в логе видно только «DLL загружена» и сразу «DLL выгружается».
  Так что для Steam-копии используйте `Запустить с переводом.bat` или
  Launch Options (способ 2 и 3 выше), а не `TranslatorLauncher.exe --launch` по
  прямому пути к exe.
- После обновления игры `locale_patch` нужно пересобрать (`update_patch.py`,
  см. раздел про обновления выше). Полностью избавиться от этого шага можно
  было бы, научив саму DLL доставать оригинальные чанки из exe и патчить их
  в памяти на лету — алгоритм разбора `.rdata` уже есть в
  `tools/extract_assets.py`, останется добавить в DLL brotli и перенести
  туда же поиск функции инициализации локалей. Тогда патч подходил бы к
  любой версии игры сам.
- Используйте это только для однопользовательских/офлайн игр и с учётом
  лицензионного соглашения игры — инжект DLL и хуки WebView2 не
  предназначены для игр с анти-читом или онлайн-составляющей.
